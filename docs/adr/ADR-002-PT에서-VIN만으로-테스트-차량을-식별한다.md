## 맥락과 문제

WAY의 기존 PT 설계는 사전 등록한 `VIN`과 `X-Device-Id`가 모두 일치하는 차량 앱에 가상 픽업 접근을 허용한다. 저장할 차량 키는 등록된 VIN이다. 재원은 PT가 가상 픽업의 서버 연동을 보여주는 자리라는 점에서 차량 식별 헤더를 하나로 줄이는 방안을 검토했다. 이후 에뮬레이터에서 VIN을 조회할 수 있다는 내용을 전달받았다고 공유했다. [기존 WAY 서버 맥락](../project-context.md#채택한-mvp-결정) · [VIN 단독 전환 논의](codex://threads/01a1f825-2611-7ce1-be8b-63ff5413eb41)

## 결정과 이유

가상 데이터를 사용하는 PT에서 차량 앱은 Pleos Vehicle SDK로 읽은 값을 `VIN` 헤더로 보낸다. 팀은 시연 대상 VIN을 시연 DB의 `vehicle` 테이블에 기본 키인 `vehicle_key`로 사전 등록한다. 서버는 헤더의 VIN으로 등록 차량을 조회한다. 픽업 생성 시에는 조회한 차량을 소유 차량으로 연결한다. 차량 권한이 필요한 REST 요청과 WebSocket 연결에 같은 식별 기준을 적용하고, 대상 픽업에 대한 차량 권한도 확인한다.

에뮬레이터에서 읽은 VIN을 기존 차량 키로 바로 사용할 수 있다. 팀이 준비할 값은 시연용 VIN이며, 기기 ID의 발급·수집이나 차량 키로의 별도 매핑이 필요 없다. [Vehicle 엔티티](../../src/main/java/com/hyundai/way/domain/vehicle/domain/Vehicle.java)

등록 목록을 파일과 DB에 각각 두면 같은 VIN을 두 곳에서 관리하게 된다. `vehicle` 테이블을 등록 기준으로 쓰면 기본 키 조회 한 번으로 등록 여부를 확인하고 픽업과 연결할 차량을 얻을 수 있다.

## 검토한 대안

- **`VIN`과 `X-Device-Id`를 함께 검증**. 같은 VIN을 제시해도 등록한 기기 ID와 일치하는지 검사할 수 있다. 앱과 서버가 두 값을 전달하고 관리해야 하므로 가상 데이터 시연에서 요구하는 식별 범위에 비해 준비 작업이 많다.
- **`X-Device-Id`만 사용**. 헤더 수는 한 개로 줄어든다. 기존 VIN 기반 차량 키를 쓰려면 기기 ID를 정해 수집하고 차량 키에 연결해야 한다. 에뮬레이터에서 읽은 VIN을 바로 쓰면 이 절차를 줄일 수 있다.
- **앱 시작 시 조합을 등록하고 세션을 발급**. 이후 요청에 서버가 발급한 자격 증명을 재사용할 수 있다. 최초 등록을 승인할 근거와 등록·만료 처리가 필요해 PT 범위에서 추가할 이점이 작다.

## 영향과 트레이드오프

- 채택 시 차량 앱과 서버의 REST·WebSocket 계약을 `VIN` 헤더 하나로 맞춘다. 픽업 소유권과 `(vehicle_key, request_id)` 재시도 식별에는 동일한 차량 키를 사용한다. [픽업 생성 명세](https://app.notion.com/p/41a335044a448018a3cad0c414b23257) · [실시간 통신 명세](https://app.notion.com/p/418335044a4480feb7aac3878bb41f0f)
- 등록된 VIN을 제시한 요청은 모두 같은 차량으로 식별된다. 이 제약은 가상 데이터로 진행하는 PT에서 감수한다. 실제 동승자 위치를 공유하기 전에는 호출자 인증과 계정에 차량 관리 권한을 부여하는 절차를 정한다. 휴대전화 인증과 회원가입은 그때 검토한다.

## 검증

에뮬레이터의 VIN 조회 가능 여부는 전달받은 내용이다. 실제 시연 환경에서 반환되는 값과 서버 연동은 다음 확인이 필요하다.

- [ ] 시연에 사용할 에뮬레이터를 재기동한 뒤에도 차량 앱이 동일한 VIN을 읽는지 확인한다.
- [ ] 등록된 VIN으로 가상 픽업 생성·조회와 WebSocket 연결이 되는지 확인한다.
- [ ] VIN이 누락되거나 미등록이면 차량 요청이 거부되고, 등록된 다른 차량도 해당 픽업에 접근할 수 없는지 확인한다.
